Why .claude/rules waits and CLAUDE.md doesn't

Two markdown files sit in the same repo and both tell Claude how to write code. One is in the prompt from the first turn of every session. The other shows up only when Claude reads a matching file, and sometimes after the code it was meant to govern is already written. This post shows how Claude Code decides what goes into the prompt, and when.

Post 67·~12 min·5 interactive panels·Every load rule cited to the Claude Code docs

1 · The question

Here is the question that prompted this post. In an explorable of a Claude Code repo, CLAUDE.md is labelled loads every session and .claude/rules/api.md is labelled loads on a matching file read. Both are markdown files that Claude Code reads, so why do they behave differently?

The short answer: the folder is not what decides it. Three lines of frontmatter are. Toggle them off and watch the label change.

CLAUDE.mdevery session

        
No trigger. Claude Code loads it at launch because it is meant for things that are true for every task:
          build commands, layout, team-wide conventions.

      

      

        
.claude/rules/api.mdon matching read

        

        

        
      

    


    
“Rules without paths frontmatter are loaded at launch with the same priority as
      .claude/CLAUDE.md.” … “Path-scoped rules trigger when Claude reads files matching the pattern,
      not on every tool use.”Claude Code docs, Manage Claude's memory


    
So .claude/rules/ is two features in one folder: a place to split a long CLAUDE.md into topic files (no
       paths, loaded at launch), and a place for conditional instructions that wait for evidence they are
       needed. The rest of this post is about the second kind: what the trigger is, why it was chosen, and the one case where it
       fires too late.

3 · The trigger is a glob

    
The paths field takes glob patterns, relative to the project root. * matches within one folder,
       ** crosses any number of folders, and {ts,tsx} expands into alternatives. You can give several
       patterns as a YAML list. Type a pattern and see which files in a slightly larger acme-shop would trigger it.

    

      

        
        
        
        
        
        
        
      

      
      

      

    

    

      Two patterns worth noticing. src/api/*.ts does not reach src/api/v2/, since one
      star stays inside one folder. And **/*.test.ts also matches a test file at the repo root, because **/
      can match zero folders. Patterns also overlap: src/web/**/*.{ts,tsx} catches src/web/Cart.test.ts,
      so reading that one file loads both the React rule and the test rule. If a rule never fires, or fires when you did not
      expect it, check the pattern first.
    

  


  
  

    
4 · Why not just load everything? The prompt is a budget

    
Everything loaded at launch rides along on every turn of the session. A team that writes one rule file per concern
       (API, tests, migrations, React, infra, analytics, auth) can end up with dozens. Use the sliders to see what loading
       them all costs compared with loading only what a session touches.

The scoped bar is an upper bound for the session: it assumes the needed rules are loaded from turn one,
        when in fact each one arrives at its first matching read.

    

    
The cost has two parts, and only one is money.

    
    
      
  • Context space. Prompt caching makes re-sent tokens cheaper, but it does not make them smaller. They still
          take up room in the window for the whole session, room that would otherwise hold code and conversation.
    • 
      
  • Attention. The docs make the adherence point directly about CLAUDE.md:
    • 
    

    
“Size: target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence.”
      Claude Code docs, Manage Claude's memory

    
A migration rule sitting in the prompt while Claude restyles a button is not neutral. It is one more instruction competing
       with the ones that matter. Path scoping is how you get many rules without making each one weaker:

    
“Rules can also be scoped to specific file paths, so they only load into context when Claude works with
      matching files, reducing noise and saving context space.”Claude Code docs, Manage Claude's memory

  


  
  

    
5 · Why the trigger is a read

    
Lazy loading needs a signal for when a rule becomes relevant. At launch Claude Code knows nothing about the task.
       After your prompt it knows some words, but words are a weak signal: "fix the cart" could mean the React component, the
       API, or the database. The first hard evidence of what a task touches is the files Claude opens. Reading
       src/api/orders.ts is about as clear a sign of API work as there is, and it usually comes before any edit,
       because you read code before you change it.

    
That last clause is where the design is right most of the time and wrong once. The table runs the three scenarios
       from section 2 under two policies and counts what goes wrong. The numbers come from the same engine that drives the
       simulator.

    

    
"Unneeded tokens" counts path-scoped rules loaded into a session that never touched a file they match. "Rule
      missing at write" counts files created in a scoped directory before their rule loaded.


    
Closing the gap

    
The read trigger is cheap and right for edits. It only misses on greenfield work. You do not have to choose between
       "always" and "lazy" for a whole rule. You can split it:

    
    
      
  • Promote the one line that must never be missed. If hand-returned status shapes are a real incident
          risk, put a single line in CLAUDE.md ("API handlers throw ApiError; see .claude/rules/api.md") and keep the details
          scoped.
    • 
      
  • Make reading the first step. "Look at orders.ts and add a refunds endpoint like it" causes the read
          that loads the rule, and gives Claude a working example as well.
    • 
      
  • A nested CLAUDE.md is not the fix. src/api/CLAUDE.md also loads on read, so it has the
          same gap as the rule it would point to.
    • 
    

  


  
  

    
6 · The same idea, all the way down

    
Path-scoped rules are one rung on a ladder that runs through all of Claude Code's instruction files: load the
       cheapest summary early, and the full text only when there is evidence it is needed.

    

      
at launch

        CLAUDE.md and CLAUDE.local.md in the working directory and every directory above it,
        ~/.claude/CLAUDE.md, the managed-policy CLAUDE.md, every rule without paths (project and
        ~/.claude/rules/), every @import those files pull in, and each skill's description.

      
on read

        Rules with paths, when Claude reads a matching file. CLAUDE.md / CLAUDE.local.md in
        a subdirectory of the working directory, when Claude reads a file in that subdirectory.

      
on invoke

        A skill's full SKILL.md body, when the skill runs. It then stays for the rest of the session.

      
after /compact

        The project-root CLAUDE.md is re-read from disk and re-injected. Nested CLAUDE.md files and paths: rules
        are not; they reload the next time Claude reads a file they apply to. So the catch from section 2 can come back
        after a compaction.

    

    

      Two misreadings to avoid. First, @imports are not lazy: "imported files are expanded and loaded
      into context at launch alongside the CLAUDE.md that references them", so splitting a big CLAUDE.md into imports
      organises it without shrinking it. Use path-scoped rules or skills for that. Second, user rules and project rules do not
      override each other: user rules load first, and "if a user rule and a project rule conflict, Claude may follow either one."
    

  


  
  

    
7 · Where does this instruction belong?

    
The question to ask for any instruction is when does it need to be true? Every task, one area of the code, one
       procedure you run sometimes, or only on your machine. Pick a home for each instruction below.

    

    

  


  
  

    
8 · Seeing what actually loaded

    
When a rule seems to be ignored, the first question is whether it was in context at all. Claude Code gives you three tools for this:

    
    
      
  • /context lists the CLAUDE.md and rules files loaded into the current session, under Memory files.
    • 
      
  • /memory lists your CLAUDE.md, CLAUDE.local.md and other memory file locations across user and project scopes.
    • 
      
  • The InstructionsLoaded hook fires whenever an instruction file loads, with the reason as its matcher value:
          session_start, nested_traversal, path_glob_match, include or
          compact. It is for observing only and cannot block a load.
    • 
    

    
To log every path-scoped load to a file, add this to .claude/settings.json:


{
  "hooks": {
    "InstructionsLoaded": [
      {
        "matcher": "path_glob_match",
        "hooks": [
          { "type": "command", "command": "cat >> ~/.claude/instructions-loaded.log" }
        ]
      }
    ]
  }
}

    
The hook receives the event as JSON on stdin; this one just appends it. See the
      hooks reference for the payload fields.

  


  
  

    
9 · PM lens: instructions are a product surface

    
If your team ships with Claude Code, the instruction files are part of the product: they decide how consistent the
       output is. Questions worth asking:

    
    
      
  • "How many lines load before anyone types?" Run /context in a fresh session. If the always-on
          instructions are over a couple of hundred lines, adherence is already being traded for coverage.
    • 
      
  • "Which rules have never fired?" An InstructionsLoaded log over a week shows which
          paths: rules loaded. A rule that never loads has a broken glob, or describes code nobody touches.
    • 
      
  • "What breaks if this rule loads late?" Sort scoped rules by the cost of the greenfield miss. A style
          preference can wait. A security or money-handling invariant earns one line in CLAUDE.md.
    • 
      
  • "Is this an instruction or a procedure?" A checklist you run sometimes (release, incident review) is a
          skill: description always loaded, body on demand. A fact about the code is a rule.
    • 
      
  • "Is it personal?" Ports, test accounts and personal style go in CLAUDE.local.md or
          ~/.claude/, not in the committed files every teammate pays for.
    • 
    

    

      The single most useful mental model. Instructions loaded at launch are paid for by every task. Path-scoped
      ones are paid for only by tasks that touch matching files. The read trigger is what makes the second kind possible, and
      also why it can arrive late.
