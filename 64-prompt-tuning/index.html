Prompt Tuning —
Teaching a Frozen Model New Tricks

You can't change the model. You can only change what you put in front of it. It turns out that's enough — if you stop restricting yourself to words. An interactive walkthrough of soft prompts, with a lab where you actually train one.

🗄️ The problem: a photocopier for 11-billion-parameter models

Fine-tuning works. That was never in doubt. The problem is what fine-tuning produces: a complete, private copy of the model, one per task.

Ten tasks, ten copies. A hundred customers with a hundred custom behaviours, a hundred copies. Every copy has to be stored, versioned, loaded into GPU memory, and served on its own. Batching requests across tasks becomes impossible, because no two requests share weights.

The reframing: if the model never changes, the model is infrastructure. What varies per task is a file small enough to email. Prompt tuning is the attempt to make that file as small as it can possibly be — and the paper's headline claim is that at sufficient scale, you lose nothing for it.

🔤 Hard prompts vs. soft prompts

You already know how to steer a frozen model without touching its weights: write a better prompt. "Classify the sentiment of the following review:" That's a hard prompt — hard as in discrete, made of real tokens from a real vocabulary.

Here's the catch nobody points out. Once your words hit the embedding layer, they stop being words. Each token becomes a vector in continuous space — for T5‑XXL, a point in 4096 dimensions. Prompt engineering is therefore a search problem with a brutal constraint: you may only land on the ~32,000 points that happen to correspond to tokens. Everything in between is unreachable by typing.

A soft prompt drops the constraint. Instead of choosing tokens and letting the embedding table decide the vectors, you optimise the vectors directly. They are still prepended exactly where token embeddings would go — the model can't tell the difference — but they are free parameters, and they almost never correspond to any real word.

Why this matters more than it sounds: the vocabulary is a vanishingly thin scattering of points in a 4096‑dimensional space. Prompt engineering searches that scattering by hand. Prompt tuning does gradient descent over the whole space. The reachable set isn't slightly bigger — it's a continuum versus a finite set.

⚙️ What actually changes (and what doesn't)

The mechanism is almost anticlimactically simple. Take your input x, embed it as usual into a matrix of shape n × d. Now prepend a second matrix P of shape k × d — k learnable vectors, same width as the embeddings. Feed the concatenation to the model.

Y = Modelθ( [ P ; E(x) ] )    where  P ∈ ℝk×d
maximise  log pθ;P(Y | [P;E(x)])   w.r.t. P only  ·  θ frozen

Training runs normally — forward pass, loss, backward pass. Gradients flow all the way back through every frozen layer, because they have to in order to reach P. But when the optimiser step comes, only P moves. Every weight in θ receives a gradient and then ignores it.

Watch which blocks light up on the backward pass.
The cost nobody mentions: backprop still traverses the entire 11-billion-parameter network. Prompt tuning saves storage and serving cost, and it saves optimiser state — but a training step is nearly as expensive as full fine-tuning. It also eats context: a 100‑token soft prompt is 100 tokens of sequence length you pay for on every single inference call, forever.

Three things to try

1 · Compare the ceilings. Train on Task A, then Task B. Task A reaches 100% accuracy; Task B barely improves on its starting point no matter where you put the prompt — you can read it straight off the landscape, which has no deep basin anywhere. A prompt steers capability the model already has. It cannot add capability the model lacks. This is the single most useful intuition for a PM: prompt tuning is a routing problem, not a teaching problem.
2 · Turn on Hard mode. Now the prompt can only sit on one of the 60 vocabulary dots, and "training" degenerates into searching them. On Task A, the best discrete token lands at a visibly worse loss than the continuous optimum sitting between the dots. That gap — small here, larger in 4096 dimensions — is the entire reason soft prompts exist.
3 · Pick the unlucky random init. The zero, vocabulary and class-label inits all converge to the same optimum on Task A. The random one starts elsewhere on the landscape and settles into a different, worse minimum — same frozen model, same task, same learning rate, worse answer purely because of where it began. This is not a quirk of the toy: the paper finds initialisation matters a great deal at small model sizes, and stops mattering at 11 B. Bigger models have friendlier landscapes.

🏗️ Where the new parameters live

Prompt tuning is one point in a family. The family members differ on one question: where in the network do you insert the trainable bits? Everything else — freeze the backbone, train something small — is shared.

Full fine-tuning

Prompt tuning is the strict simplification. Prefix tuning (Li & Liang, 2021) inserts trainable vectors into the attention keys and values of every layer, and needs an MLP reparameterisation to train stably. Lester et al. showed that if the model is big enough you can throw all of that away — one matrix at the input, no reparameterisation — and still match full fine-tuning. Fewer moving parts, same result, but only above a certain scale.

📈 The power of scale — the finding the title is about

Here's what makes this paper more than a storage trick. At small model sizes, prompt tuning is clearly worse than fine-tuning the whole model. The authors ran the same experiment across five T5 sizes and found the gap shrinks monotonically — and at 11 B parameters it closes entirely.

Why would scale help? The paper doesn't fully answer this, and it's worth being honest that it's an empirical finding rather than a derived one. The intuition offered is that a larger frozen model already contains a richer set of behaviours, so the job of the prompt shifts from teaching to selecting — and selecting needs far fewer bits than teaching. You can feel this in the Lab: the prompt is only ever moving you around a landscape the frozen model already defines.

One methodological detail that matters more than it should

None of this works on stock T5. T5's pre-training objective is span corruption, and a model trained purely on it never learns to emit natural, well-formed text — so prompt tuning on top of it is unstable, and mid-sized models produce invalid class labels outright. The authors had to continue pre-training with a language-modelling objective for 100 K steps (10% of the original T5 pre-training budget) before prompt tuning behaved. Adding a sentinel token helped little; only real LM adaptation did.

PM translation: "parameter-efficient" is a claim about the adaptation step, and it can quietly depend on an expensive preparation step upstream. When you're evaluating a PEFT method for a roadmap, ask what the base checkpoint had to go through first.

🔧 What actually moves the needle

Three design choices, and a consistent pattern across all of them: each one matters a lot at small scale and stops mattering at large scale.

How many virtual tokens do you need? The authors swept 1, 5, 20, 100 and 150.

1Surprisingly viable at XXL; substantially worse at every smaller size.

Read this as a cost dial. Every virtual token is sequence length you pay for on every inference request. Going 100 → 20 cuts your per-task artefact and your per-call overhead 5×, and above a billion parameters the accuracy cost is small.

The model was, in a sense, already told the answer format — the prompt just needed permission to say it in vectors. And at XXL the whole effect vanishes: every initialisation converges to the same quality.

🎁 Two properties you get for free

1 · Ensembling becomes almost costless

Train N prompts for the same task, and you have N models — sharing one frozen backbone. You don't run N forward passes on N models; you build one batch where each row carries a different prompt, and a single forward pass gives you the whole ensemble.

2 · It transfers out of domain better than fine-tuning does

This is the result that should make you sit up. A fully fine-tuned model can bend its own weights to fit the training distribution — including its quirks. A frozen model can't, so the prompt has less room to overfit to the domain. Train on one distribution, test on another, and prompt tuning wins:

Zero-shot domain transfer, F1 unless noted. QQP→MRPC accuracy: 73.1 ± 0.9 (model tuning) vs 76.3 ± 0.1 (prompt tuning). All numbers from Lester et al. (2021).
The +12.5 F1 on TextbookQA is the standout: the target domain furthest from SQuAD is exactly where freezing the backbone pays off most. Constraint as a regulariser.

🧭 The PM lens — should you actually use this?

Honest answer: in 2026, usually not, and it's worth understanding why a technique can be this elegant and still lose.

LoRA won the practical fight. It trains faster, is less sensitive to hyperparameters, doesn't consume context window, can be merged into the base weights at inference for zero added latency, and — critically — the whole ecosystem (adapters, hubs, serving stacks) standardised on it. Prompt tuning's per-task artefact is smaller, but LoRA's is already small enough that nobody's storage budget is the binding constraint.

What prompt tuning is still genuinely good for: extreme multi-tenancy where you're serving thousands of task variants off one backbone and want them batched together in a single forward pass; settings where you must not modify the served weights at all, for audit or contractual reasons; and out-of-domain robustness, where the frozen-backbone constraint is a feature. It also remains the cleanest mental model for understanding why every PEFT method works, which is worth the twenty minutes on its own.

Limitations worth writing on the roadmap

  • Training isn't cheap. Backprop traverses the full frozen model. You save optimiser state and storage, not compute.
  • Convergence is slow. 30,000 steps at a learning rate of 0.3 with batch size 32 — an aggressive LR precisely because the gradient signal reaching a handful of input vectors is weak.
  • It costs context forever. A 100-token prompt is 100 tokens of every request's sequence budget and attention cost, for the life of the deployment.
  • Interpretability is gone. A hard prompt can be read, reviewed, and shipped through a content-review process. A soft prompt is a matrix of floats that corresponds to no words — you cannot review it, and you cannot explain it to a regulator.
  • It cannot add knowledge. The Lab's Task B is the demonstration: if the frozen model can't do it, no prompt vector will make it. Confirm capability exists before budgeting for adaptation.
  • Small models need not apply. Below roughly a billion parameters the gap to fine-tuning is real and the design choices become finicky.

✍️ Exercises

  1. In the Lab, train Task A from the zero init, note the final loss, then switch to Hard mode and search all 60 tokens. Write down the gap. Now argue why that gap would grow rather than shrink in 4096 dimensions.
  2. Task B's landscape has no deep basin. Before running anything, predict what accuracy it converges to — then check. What would you actually have to change to solve Task B, and which of the five methods in "Where the new parameters live" would you reach for?
  3. Use the cost calculator: at what prompt length does T5‑Small's per-task artefact exceed T5‑XXL's at k=5? What does that tell you about comparing PEFT methods across model scales?
  4. The paper's domain-transfer result shows the biggest win on the most distant domain. Design an evaluation for your own product that would detect this effect — and explain why an in-distribution holdout set would miss it entirely.
  5. Write the one-paragraph case against prompt tuning that you'd expect from an infra lead. Then write the rebuttal for the extreme-multi-tenancy scenario.
